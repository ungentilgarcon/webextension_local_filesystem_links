# Build from source

These instructions are for contributors and users who need to build the browser
add-on or native host themselves. The supported ready-to-install browser is
Firefox. Although a Chrome manifest is included in the source, the native-host
registration currently targets Firefox only; Chrome is not a supported setup.

## Build the Firefox add-on

Install Node.js/npm, then run these commands from the repository root:

```sh
npm install
npm run build
npm run bundle
```

The production extension is written to `dist/`; the installable ZIP is written
to `web-ext-artifacts/`. The Firefox ZIP can be installed in Firefox or
submitted to [Firefox Add-ons](https://addons.mozilla.org/en-US/developers/addon/local-filesystem-links/versions).

For development only, the Chrome manifest can be selected by setting
`BROWSER=chrome` when running the webpack build. This does not add Chrome native
messaging support, so local file links will not work end-to-end in Chrome.

## Build the Windows native host

Install 64-bit Python 3.15 and Inno Setup 6. During Python setup, enable
**Add Python to PATH**. From the repository root, install the native-host
dependencies and run its tests:

```powershell
py -3.15 -m pip install -r native-host\requirements.txt
py -3.15 -m unittest discover -s native-host\tests -v
```

Then build the host from `native-host/` using Git Bash (installed with Git for
Windows) and compile the installer from PowerShell:

```sh
cd native-host
sh build/build.sh
```

```powershell
& "${env:ProgramFiles(x86)}\Inno Setup 6\ISCC.exe" "native-host\build\windows\InnoSetupScript.iss"
```

The installer is written to `native-host/bin/win32/native-app-setup.exe`. It
registers the absolute host executable path for Firefox. Optional diagnostic
logging is disabled by default and can be enabled in the installer. If the
Python launcher or `pyinstaller` command is not found, rerun Python setup and
enable **Add Python to PATH**, then open a new terminal.

## Linux native host

The current GitHub release does not include a prebuilt Linux native host. The
Linux build uses Python 3.15 and the PyInstaller version pinned in
`native-host/requirements.txt`. The native host currently registers with
Firefox, not Chrome.

On a Linux build machine, install Node.js/npm and Python 3.15. Install the
native-host requirements, then build from the repository's `native-host/`
directory:

```sh
python3.15 -m pip install -r requirements.txt
npm install
npm run build:unix
```

This creates `native-host/bin/linux/native-app-bundle-linux.tar`. From
`native-host/`, extract the archive into a directory that will remain in place
and register the native host for the current Firefox user:

```sh
mkdir -p "$HOME/local-filesystem-links-host"
tar -xf bin/linux/native-app-bundle-linux.tar -C "$HOME/local-filesystem-links-host"
cd "$HOME/local-filesystem-links-host"
chmod +x install_host_compiled.sh
./install_host_compiled.sh
```

Keep the extracted host files in place after installation: the registered
manifest points to the executable inside that directory. Restart Firefox after
installing. The installer writes the native-host manifest under the current
user's Mozilla configuration.

## Publish a Firefox add-on

Before submitting a new version, update the version in `package.json`, build
and bundle the extension, then upload the ZIP from `web-ext-artifacts/` to
[Firefox Add-ons](https://addons.mozilla.org/en-US/developers/addon/local-filesystem-links/versions).
Follow Mozilla's submission steps and provide the source archive generated by
`./make-sourcecode-archive.sh` when requested.

## Create a GitHub release

GitHub Actions builds the signed Firefox add-on and Windows installer when a
version tag is pushed. It creates a **draft** release so the assets and notes
can be checked before they are published. No Linux host package is built by
this workflow.

### One-time repository setup

In the GitHub repository, open **Settings → Secrets and variables → Actions**
and add these repository secrets from the Firefox Add-ons API credentials:

-   `AMO_JWT_ISSUER`
-   `AMO_JWT_SECRET`

The workflow requires these secrets to sign the Firefox package. Do not put
them in the repository or in workflow files.

### Release steps

1. Update the extension version in the root `package.json` and the native-host
   version in `native-host/package.json`. The release tag must exactly match
   the native-host version, for example `v0.2.16`; the add-on version is
   recorded separately in the release notes and asset filename.
2. Update `CHANGELOG`, run the relevant builds/tests, commit, and push the
   release changes to `master`.
3. Create and push the version tag from that commit:

    ```sh
    git tag v0.2.16
    git push origin v0.2.16
    ```

4. In **Actions**, check that the Firefox signing and Windows installer build
   jobs succeeded. The workflow creates a draft GitHub release with the signed
   add-on and Windows installer, including versioned assets.
5. Review the generated release notes and download both assets from the draft
   to verify them. Then publish the draft in **Releases**.

Do not reuse a published tag. For another release, increment the native-host
version and create a new matching tag.
